# Support

Use the narrowest GitHub surface that matches the request so work is routed with the right evidence and authority.

- **Bug with a reproducible failure:** open the Bug Report issue form and include the exact command, exact subject SHA, observed output, and current standing.
- **Feature or capability gap:** use the Feature Request or Capability Gap form. Describe the desired invariant and the falsifier that would prove it is implemented.
- **Developer-experience / quality-of-life issue:** use the DX / QoL form and identify the repeated friction, affected journey, and measurable improvement.
- **Documentation problem:** use the Documentation form and name the page, audience, and missing or stale information.
- **Security vulnerability:** do not open a public issue. Use GitHub Security Advisories as described in `SECURITY.md`.

Before opening an issue, run the cheapest relevant read-only diagnostic when possible: `just doctor`, `just next`, `just explain`, or `just github-dx`. Attach real output rather than a paraphrase.

Support requests do not confer mutation or release authority. `ALIVE`, `PARTIAL_ALIVE`, `BLOCKED`, `BUILD_BROKEN`, `UNSUPPORTED`, `REFUSED`, and `UNKNOWN` remain scoped evidence-backed standings, not conversational labels.
